# P2.1 prototype: vector store

Status: **results for the author's decision** · 2026-10-23 · code in `prototypes/vector_store/`

The question: where do passage vectors live? The candidates were LanceDB (embedded), Qdrant (a server) and Neo4j's vector index (already chosen as the graph store). The deciding workload, from the overview and phase2-design.md, is **filtered kNN**: by entity (passages in documents mentioning X) and by date, plus continuous appends from the enricher's micro-batches and survival of power loss.

## Setup

- **Corpus:** the whole archive. 256k documents became **1,224,137 passages** (`seg-1`: median 174 words, 4.8 per document), embedded with **bge-m3** (1024-d, fp16 on the 5060 Ti at 154 passages/s, 133 min; 2 GB VRAM).
- **Queries:** 200 real headlines from the archive, embedded with the same model.
- **Workload:**
  - bulk-load 1.18M passages and build the index;
  - append the last 40,000 in micro-batches of 2,000;
  - search the top 50: unfiltered, last 7 days, and gated to random document sets of 100 / 1,000 / 10,000 documents (a stand-in for "documents that mention entity X"), plus gate and date combined.
- **Truth:** exact top-50 computed on the GPU. Recall@50 is measured against it.
- **Versions:** LanceDB 0.40 (IVF-HNSW-SQ, BTree scalar indexes); Qdrant 1.19.2 (HNSW, int8 scalar quantization in RAM, originals on disk, keyword and integer payload indexes); Neo4j 2026.09.0 Community (vector index with `doc_id` and `published` as filter properties, Cypher 25 `SEARCH … WHERE`).

## Results

**Defaults** (each engine out of the box):

| | LanceDB | Qdrant | Neo4j |
| --- | --- | --- | --- |
| Bulk load (1.18M) / index build | **8 s** / 138 s | 44 s / **27 s** | 829 s / 88 s |
| Append 2,000 rows (p50) | fast; rows unindexed until `optimize` | indexed in the background | slow over bolt |
| Unfiltered: p50 / recall | 4.7 ms / 0.855 | 4.8 ms / 0.925 | 9.5 ms / 0.878 |
| Last 7 days | 26 ms / 0.88 | 4.3 ms / 0.91 | 13 ms / 0.90 |
| Gate of 100 / 1k / 10k docs: recall | 0.98 / 0.98 / 0.98 | 0.97 / 0.97 / **0.53** | 0.995 / 0.97 / 0.95 |
| Disk (1.22M passages) | 6.8 GB | 7.1 GB | **16.7 GB** |

**Tuned** (more search effort; the stores were re-used):

| | LanceDB (`nprobes` 40, `ef` 200, `refine_factor` 2) | Qdrant (`hnsw_ef` 256, ACORN, oversampling 2 + rescore) |
| --- | --- | --- |
| Unfiltered: p50 / p95 / recall | 8.1 / 11.4 ms / 0.945 | 23.8 / 108 ms / **0.972** |
| Last 7 days | 29 ms / 0.95 | **9.9 ms** / **0.97** |
| Gate of 100 / 1k / 10k docs: p50 | 22 / 33 / 65 ms | **2.2 / 3.9** / 54 ms |
| Gate of 100 / 1k / 10k docs: recall | **0.997 / 0.996 / 0.995** | **0.997 / 0.996 / 0.994** |

ACORN (Qdrant's filtered-HNSW mode) fixed the 10k-gate collapse, from 0.53 to 0.994. Neo4j has no query-time effort setting.

## Findings

1. **Neo4j Community can't be the vector store.** Its compact native `VECTOR<FLOAT32>` property needs the *block* store format, which is Enterprise-only ("storing properties of type vector is not supported in aligned store format"). In Community, vectors are stored as 64-bit double lists: **about 13.7 KB per passage, 2.4× the others**, roughly 1 TB a year at our volume. Its bulk load over bolt is also about 100× slower. **Neo4j stays the graph store only.**
2. **Qdrant and LanceDB both reach about 0.995 recall on entity-gated searches.** That's the query the product depends on. Qdrant is about 10× faster on small and medium gates (2–4 ms vs 22–33 ms) and on date filters. LanceDB is faster unfiltered at similar recall. Either is far below the query path's budget, where stance judgment takes about 1 s.
3. **Freshness:** Qdrant indexes new points in the background, so they're searchable immediately at full speed. LanceDB serves appended rows by a flat scan until `optimize()` (search went from 4.7 to 26 ms with a 40k-row backlog), so the enricher would have to optimize regularly.
4. **Disk is the real long-term cost, whichever engine wins.** Both store the original float32 vectors next to the compressed index: about **5.5–5.8 KB per passage, about 400 GB a year** at about 200k vectors a day. Vectors are kept for the full archive (decisions.md), so the **stored format must shrink**. Levers, to settle together with the model evaluation:
   - store originals as float16 (Qdrant `datatype=float16`; LanceDB fp16 columns): about half;
   - fewer dimensions through a Matryoshka model (Qwen3-Embedding at 512-d): about half again. bge-m3 isn't Matryoshka.
   - Together, that's roughly 100–140 GB a year: years of headroom on the 2 TB disk, and a second disk later is cheap.
5. **Crash safety (Qdrant): 10/10 PASS.** `crash_qdrant.py` SIGKILLed the container during acknowledged (`wait=True`) writes, after 12 to 77 acknowledged batches of 500. After every restart, every acknowledged batch was complete and the collection was searchable and green. **Caveat:** this simulates a process crash, not a power cut, where writes not yet flushed to disk could still be lost. A Qdrant power-pull test belongs in Phase 2's soak (G2.4). The impact would be bounded: vectors are derived data, and the enricher re-queues anything missing.

## Recommendation

**Qdrant for vectors, Neo4j for the graph.**
- **Why Qdrant:** the fastest gated and date-filtered search at equal recall; mature payload filtering (keyword `MatchAny` for entity gates, integer ranges for dates, ACORN for selective filters); online indexing, so new passages are searchable at full speed with no optimize step; snapshots for backup. It's already running in Docker next to Neo4j.
- **Settings to start with:** int8 quantization in RAM, originals on disk (float16 once tested), payload indexes on `doc_id`, `published`, `source_id` and the entity IDs, ACORN on for gated queries, and `hnsw_ef` about 128–256, tuned on the Phase 2 eval queries.
- **Fallback:** LanceDB, if running a third service ever becomes a burden. It's embedded, file-based, and matches recall, at about 10× the gated latency.
- **Still open for the model evaluation:** the embedder (bge-m3 vs Qwen3-Embedding), the dimensions and the storage precision. The disk forecast depends on these more than on the engine.
